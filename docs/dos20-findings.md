# DOS 2.0: the display audit (November 2026, begun)

*DOSHO.EXE, 2.0.1 (English) and the German 2.0 build; the same game as Windows 3.1 and Mac 2.0.1 (`docs/dos-findings.md`).*

- **Programs** (private repo: `extracted/dos-2.0.1`, `extracted/dos-2.0-German`; `decompiled/dos-2.0.1`, `dos-2.0-German`): every DOSHO.EXE on the archive.org disks and in the `Spaceward_Ho_1992.zip` install tree is the one English build (md5 5d230351...).
  The German one (17 Feb 1993, 523,840 bytes) is not PKLITE-packed. Its HOMONO.PRS and HOCOLOR.PRS came out round-sized (the disk image is probably one disk of a set).
- **Decompile.** PKLITE unpacked by emulation (`tools/decompile/dos-unpack.py`, unicorn); the Borland VROOMM overlays (49) relocated and loaded at segments 0x9000 up, their INT 3Fh stubs patched to far jumps
  (`dos-flat.py`; the stub-header format is written in `decompiled/dos-2.0.1/HOW.md`); Ghidra real mode with DS set (`DosHo.java`); 1,965 (English) and 1,976 (German) routines. The segment numbers are the ones this repo already quotes
  (`FUN_9000_0cd5`).
- **Table:** `docs/display/dos20.json` (`node tools/display-audit.js dos20`): one row for every English routine: 1,535 internal (no string, no video or BIOS access, no call of a drawing routine), **430 open** display candidates, each
  with why. The German build is the same code with its own words (not tabled separately). The program has no named API, so a routine that draws only through a library routine two calls deep is not told apart; that limit is in each internal row.
- **Skin:** the `dos` skin (`js/skins/dos`), OS look `dos`; none of the 430 has been compared yet.

## The screens (compared against the running original, November 2026)

The DOS program runs in DOSBox (the install tree's `HO!.CFG`, `SOUNDRV.COM` beside the extracted files; the English build, keyboard driven through X11 test events). Screenshots are in the scratch folder of the session (`v20dos-orig-*.png`, `v20dos-remake-*.png`); the program's windows are the Windows 3.1 dialog templates of `docs/win20-findings.md` drawn by its own window library (title bar, bold monospace text, red hot-key letters, 3-D buttons).

- **Frame:** a 640x480 screen: title bar "Spaceward Ho! - jake in MilkyWay in 2000", menu bar `File  Options  Ships  Galaxy  Window` (no Help), left column of three panels (planet numbers and the three-bar chart; fleet list box with "Stationed at: ..." / Fuel, Speed, Scrap; money lines and the budget bars; Tech Spending chart), the map on the right with an "End Turn Ctrl+T" button. The dos skin shows the classic page: a card panel, the map, its own menu names. **Not rebuilt** (gap): this whole frame and the panels' layouts.
- **Menus (fixed here):** File: About Ho!..., New Game..., Open Game..., Save Game [Ctrl+S], Revert To Saved, Close [Ctrl+W], End Turn [Ctrl+T], End Turn & Switch Players [\], Exit. Options: Force Turn Update, Auto Play..., I'll Update Turns, Set Polling Time..., Set Battle Speed..., Show Event Messages, Review Announced Battles, Give Overspending Warnings, Sound (the last four checked with a diamond). Ships: List Ship Types..., Create New Ship Type..., List All Fleets..., Organize Ships..., Build Ships at <star>..., Scrap Current Fleet, No Battles here.... Galaxy: Compare Players..., List All Explored Stars..., Send Message..., Zoom In, Zoom Out, Fix Spending. Window: Tech Spending, Reports. The dos skin lays its commands out in that order (`menuLayout` in `js/skins/dos/ui.js`, key texts "[Ctrl+S]" through `T.keyName` in the classic skin); commands the remake lacks show dimmed as the original's do when idle (Save Game, Revert To Saved, I'll Update Turns, Set Polling Time: a browser saves every change and has no network polling), the remake's own commands follow at the end of the last menu. Kept differences: "…" for "...", Set Battle Speed… opens the remake's Preferences, Create New Ship Type… opens the Build window (which holds the designer), Exit and Close both go to the title, the check diamond is the classic check, Tech Spending is not a menu item (the panel is always shown), the review-battle and organize words are the classic ones.
- **Windows seen, all unbuilt (gaps):** About (picture, "Licensed to:" lines, OK), Startup (Open Game / New Game / Cancel over the title picture), New Game file window (Filename, Directory, Files, Directories: a kept difference), Create New Galaxy (picture buttons for density, style, size, computer intelligence, a "Number of Computer Players" slider, Cancel / Create; the remake's New Game is a long form), Player Entry, New Player Registration (Skill Level, Sex, Join), Ship Types (list, picture, Rename, OK, Scrap This Type), New Ship Type (Name, Range/Speed/Weapons/Shields/Mini sliders, Class list, costs, Name It For Me / Cancel / OK), List of All Fleets, Shipbuilding queue, List of All Explored Stars (name, temperature, gravity, metal, owner), Battle Speed (with "Fully Animated Battles"), Auto Play (three radio buttons and a seconds slider), Compare Players ("Sorry, no comparisons until the year 2010." with Show Skills).
- **The 129 gap rows of the first table** were read again: 68 are settled (run-time, loaders, sound driver, resource files, file prompts, hot-seat texts, the fleet block, the planet panel, the Game Info sentence, the "--more--" pager); **61 are not settled**: routines of the program's own window library and game windows (9000-c000 overlays, the 5,158-line a000:328b, a000:c80c, 9000:76c0, b000:87fb ...) that were not traced to their window. The method that worked: `refs.json`-style scan of the code bytes for the data-segment offsets of the literal strings (846 strings in DS 0x4ea9) and for the ids of the 585 HO.PRS strings in the decompile; the Ghidra labels in the table's first notes (Version 14, Player money, WARNING ...) are unreliable names of data the code indexes. A trace with a disassembly (none is saved) would settle the rest. `node tools/display-audit.js dos20` passes (a gap does not fail it, by its own rules).
- **German:** the German build's menu and dialog words are HO.PRS's; the skin's own menu words in German come from `js/ui-text.js` (the Amiga's and DOS 2.0's German where those rows name them, ours otherwise); checked by `tools/ui-lang-audit.js dos` (en, fr, de, tr, es).

## Rebuilding the dos skin as the original's screen (November 2026, begun)

Done: the menu bar and menus are set in the program's own screen font (`tools/extract/dosfont.py` makes `assets/skins/dos/fonts/bios8x14.ttf` from HO.PRS record SFN 14, the VGA 8x14 font, one square per lit pixel), grey bar, red first letters, the green bar under the pointer, a diamond for checked items (`html.os-dos` rules at the end of `js/skins/dos/style.css`; kept difference: only the first letter of a top-level menu is red, the original reds each item's own hot key).

Measured on the running original (800x600 DOSBox screen, window at x 80-719, y 100-575): the frame is 640 x 476; title bar 15 rows (teal #009a9a, black title in the screen font), menu bar 13 rows (grey #aaaaaa), client from row 28: the left column 240 wide (white), the map black from x 240 to 631, a grey 8-pixel vertical scroll bar at 632-639, a 12-row horizontal one at the foot. The End Turn button is teal (#00cfcf) with "Ctrl+T" on a second line.

Fonts (done): `tools/extract/dospfn.py` reads the PFN records (format in its header) and makes `geneva9.ttf`, `geneva9bold.ttf` and `chicago12.ttf` in `assets/skins/dos/fonts/` (checked against the program's text: `Income : $51 ,000`, `Gorby`, `Tech Spending` come out as on screen, `v20dos-fonts-test.png`). Kept difference: the program's bold is the record `Geneva_9B` (about 1.2 times the regular's width) whose strike layout was not found, so `geneva9bold.ttf` is the regular smeared a pixel with a pixel more advance (`v20dos-bold-compare.png`). The other 15 records (italic, underlined, condensed, "V" copies) are not read.

Not done, and why (the next steps): (2) The frame must scale to the browser: a CSS transform breaks the map's pointer maths (`getBoundingClientRect`), so the scale is a `--u` unit in `calc()` with `T.mapPixel` (the Amiga skin's mechanism) rather than a transform. (3) The windows (Create New Galaxy, Battle Speed, Auto Play, Build, Compare, Fleets, About ...) from the screenshots `v20dos-orig-*.png`; the Windows templates give their rectangles.

## The dos skin as the program's screen (November 2026, state)

Built from the running program (DOSBox captures `v20dos-orig-*.png`, side by side `v20dos-sbs-*.png`; every window's outer size equals the program's to the pixel): the 640 x 476 frame (title bar, menu bar, the five boxes of the left column in HO.PRS's Geneva 9 / Geneva 9 Bold / Chicago 12, scroll bars beside the players and the budget bars, End Turn button, plain black map), the report bubble ("--more--": `bubbleMore` in `js/rules-dos.js`, the DOS pool string; "--mehr--" in the German build), and the windows Battle Speed, Auto Play, About, Create New Galaxy, List of All Fleets, List of All Explored Stars, List Ship Types, Create New Ship Type, the shipbuilding queue, Compare Players (the sentence and the chart), Reports, Organize Ships and Send Message. The default galaxy name is MilkyWay (the program's default file is MilkyWay.Ho!), the opening skill Novice; the program's player name is what the player types (the lower-case "jake" of the first captures was our key presses, not the program).
The players box lists the humans, and every player once the first turn has run, a check mark beside the ones done (observed 2000 vs 2010).

Show Skills (a second window over the chart, captured with the mouse in DOSBox, `v20dos-orig-skills.png`) and the program's alert box (captured: the fuel alert, 352 x 210, the mascot d3520, OK; `alertBox`/`confirm`/`alert` hooks in the dos skin) are built. Kept differences: the alert box's height, picture and button words for alerts other than the fuel one (not captured; the same rule is applied), Review Battle and the battle window (no battle was reached in DOSBox), the Hall windows (the remake's own; the program has none) are still the classic windows in the DOS frame (not captured or not reachable in DOSBox's keyboard-only run: a battle needs a played game; no alert was provoked); no scroll bars beside the map (the remake pans by drag); the first End Turn of the program asks "..., do you want to play alone, or wait for more humans to join?" (Wait / Continue) which the remake does not (no network join); Build: a click queues one ship, a double click removes one (the program's drag was not verified); the Rename dialog's rectangles are estimated; the Geneva colon sits one pixel tighter.


## The map's scroll bars and zoom (measured in DOSBox, November 2026)

The program's map is a window onto the galaxy: the zoom's cell is 6, 9, 12 or 17 pixels (Zoom In is dimmed at 17, where the game opens; stars 410.7 pixels apart at 17 and 290.5 at 12, ratio 0.707 = 12/17); the galaxy is `2 x its size` cells a side (the captured galaxy: 27) (a small galaxy of 14.5 has 27 cells, and the 392 x 434 pane shows 23 x 25 of them at 17, so the bars scroll 4 cells across and 2 down: measured with the arrows, one click is exactly one cell, 17 pixels). Zoom Out (12) shows the whole of such a galaxy. A star's ball is about 24 pixels at 17 and 15 at 12. The bars are drawn pixel by pixel from the captures (vertical 7 x 433, horizontal 391 x 13, arrow boxes 14 high or 8 wide, a fixed 7 x 13 / 7 x 13 thumb that rests at the far end when nothing scrolls). Built in the dos skin (`dosbar`, the `T.mapInset / syncView / centerOnStar / fitView / zoomTo / planetPx` hooks).

Taken from the Mac 1.2 program and **not measured on DOS**: a page click moves three quarters of the cells in view, a held arrow repeats every 100 ms, the thumb moves the map as it is dragged (a cell at a time), CenterOnStar's margins (40 pixels, 85 at the foot), the opening view (Zoom In on your home star; the first DOS capture had it scrolled to the bottom right, which this does not reproduce), the star icons below 12 (the program shows a dot at the smallest zoom; the remake draws the ball smaller). Dragging the map with a mouse and the mouse wheel are not in the original: with modern conveniences off they do nothing; a finger always drags.


## Review Battle, menus and the rest of the round (November 2026)

- **Review Battle** (Ships, "Review Battle at <star>…" [Ctrl+R], "No Battles here…" dimmed): the program's battle window, Windows template 7 ("Skip", 223 x 179 dialog units), 456 x 364 pixels with the program's frame, black, with 35 stars, the two sides' faces (our own without a name; a dark red cross over a side with nothing left), the groups' pictures with their words in Geneva 9 (a lost group in a stipple), the title, the result, "Round n" in Geneva 9 Bold, the winner's picture (d3500; the loser's d3510 is the Mac's rule) and a button that says OK once the shots are done. - **Menus:** the hot letter of every enabled item is red (the pool's "~" marks it; captured in all five menus); a ghosted item shows none. The German program's strings carry no "~", so only the English words are marked. The key equivalents are shown as captured (Ships: Create New Ship Type [Ctrl+K], List All Fleets [Ctrl+L], Organize Ships [Ctrl+O], Build Ships [Ctrl+B], Review Battle [Ctrl+R]; Galaxy: Compare Players [Ctrl+Y], Zoom In [+], Zoom Out [-], Fix Spending [Ctrl+F]; Window: Tech Spending [Alt+1], Reports [Alt+2]) and work where the browser lets a page have them (Ctrl+W, Ctrl+T and Ctrl+N are the browser's: kept difference). - **Alert box:** the fuel alert was captured (`v20dos-orig-alert-fuel.png`); the "Warning! … abandon them?", revert and force-turn questions were not reachable (Revert To Saved and Force Turn Update are dimmed in a one-player game; the abandon warning needs an underfunded colony). - **Show Skills:** the second window over the Compare chart (`v20dos-orig-skills.png`).
- **real-play findings, settled:** "Your Buddies/Your Allies" overflowed the Send Message cell (the caption now wraps to a second line); the program's windows have no close box (Escape or their Cancel closes them; the Reports window has the Windows control-menu mark at the left of its teal title bar, which closes it here); the android desktop/4k "destination at null" was the tool's: the target star it picked lay 6 pixels from the fleet's own dot, so the drag did not pass the click's slop (a person takes another star; the tool now needs 30 pixels).
- **The 58 gap rows** (`dos20.json`): still not settled. They are routines of the program's own windows whose screen was not identified (no names in the decompile); settling each needs the DOSBox run to reach its window.
