## The 58 gap rows (November 2026)

**How they were traced.** The overlays' far calls and far pointers were wrong in the flat image and so in the decompile: a VROOMM overlay's fixup words are not paragraph offsets but selectors, byte offsets (index x 8) into the program's segment table, which the unpacked resident image holds at linear 0x4d6d0 (149 entries: the loaded segment, the size, the kind: 0 data, 1 code, 3 overlay stub; the FBOV header names it). `dos-flat.py` added 0x1000 to each, so every overlay routine's far call named another routine (Ghidra's `func_0x00011acf`, `1118:094f` ...). The private repo's `audit/dos-2.0.1/tools/ovfix.py` rewrites the 3,814 overlay segment words from the table (en2.flat); with it the callers of the window procedures and the drawing calls are right. Two more finds made the rest quick:
- **The dialog templates.** All 32 windows are templates in a far data segment (40df:0000 on, 0x430 bytes apart, RegisterDlgBox to PatchDlgBox, `audit/dos-2.0.1/tools/tparse.py`): a name, the size in screen cells (8 x 14 pixels), and each item as x, y, height, width in cells, its control class, its words and its id. An item at cell (x, y) sits at (8 + 8x, 14 + 14y) of the window, as Battle Speed and Auto Play were measured. Each template's maker pushes its window procedure (a stub) beside it, which names the procedure of every window.
- **The window classes.** The table at DS 0x3248 (8 bytes a class: the base class, the procedure) names the controls: 3 list box (FUN_b000_0e54), 4 edit field (FUN_a000_328b), 5 menu bar (FUN_b000_2228), 6 drop-down, 7 the dialog (FUN_1000_dedf), 8 group box, 9 button, 10 combo box (FUN_9000_7f20, used by no template), 11 static text (FUN_b000_f240), 12 radio button, 13 check box, 17 status line (FUN_b000_e7f0, "F1=Help", never shown), 18 a picture item the window paints, 19 / 20 scroll bars (FUN_b000_8cb0), 21 picture button.
- **Where a window sits.** The program centres a window on its 80 x 34-cell screen in whole cells: 8 x floor((80 - columns) / 2) from the left, 14 x floor((34 - rows) / 2) from the top (all 15 captured windows: Ship Types 62 x 25 cells at 72, 56; Battle Speed at 176, 140; the fuel alert, 44 x 15, at 144, 126, which is the "7 above the middle" measured before). The dos skin centred them in the 640 x 476 frame, so Ship Types sat 7 pixels low (the brief's "30 px higher" compared two screenshots whose frames sit 38 pixels apart); every window of the skin is now placed by the rule (`placeDos`).

**Fixed** (shots looked at, scratch folder `v20dos-dg-*.png`): F10, the boss key (FUN_9000_7450: a text screen with "C:\>" until a key; captured `v20dos-orig-bosskey.png`); the End Turn button's pressed face d5001 (FUN_2000_9b03; German d5001-de); the Yes / No boxes' keys Y and N (FUN_b000_3656, 36f9); You Won and You Lost as the program's boxes YouWonDlgBox / YouLostDlgBox (FUN_9000_76c0: picture 5040 / 5050, the lines, OK); Name a Star as NameStarBox (FUN_a000_fa92: the words, picture 3500, a 7-letter field, OK, no Cancel, a taken name in the alert box); the dimmed Organize line's words "No ships to organize..." (FUN_b000_2998); the place of every window (FUN_b000_a733's Ship Types, the battle window).

**Kept:** the file window (FUN_a000_c80c, captured `v20dos-orig-openfile.png`) and the game file's loading (FUN_a000_9c76); Close's "Closing Game..." box (FUN_a000_a3e4, not seen at DOSBox's speed); the shared network file game's turn (FUN_a000_a931); the disk error box's keys (FUN_b000_37ae).

**Round 2 (later in November 2026):** the Startup window (cb68ca6, framed on the title page), the System Menu (3306b05: Move, Size, Close, Alt+Space) and the "Closing Game..." box (801513c, about a second on Close, Exit and the quit question) are built and their rows fixed; the Yes / No boxes now answer Y and N whatever the language (68857d6, with the patch's own letters and modern conveniences' whole words); the Windows look has a 16 / 256 colour choice (5a2d0e0).

## Re-check of the overlay rows with the corrected far calls (November 2026)

**Scope.** The internal rows of the overlays (segments 9000 to c000) that still carried the first table's reason, with the 44 INT 3Fh stub rows (`thunk_FUN_...`) that name them: 486 rows (the brief counted 504; the others already had a November re-trace in their reason, or are stubs whose target is a run-time routine).
**Script** (private repo, `audit/dos-2.0.1/tools/recheck_ovfar.py`; result `audit/dos-2.0.1/recheck-flags.tsv`): for every row the call graph of the corrected image (far calls, near calls and jumps, and far pointers pushed as callbacks) to a depth of 3; a row is flagged if it reaches a routine the table marks matched / fixed / notShown (the cursor and video layer count as "low", tier B, the rest tier A), has a video / BIOS / mouse instruction or a call through the video driver's vector table, pushes a dialog-template segment, uses a HO.PRS text id (624 and up; 100 to 621 are the name pools and plain numbers) or has a literal string of its own. Three rows of the table that the script must not trust were found on the way and set aside in the script: FUN_2000_fd17 is the program's event loop (its row says file windows), FUN_2000_26d3 is a bitmap routine (same), FUN_3000_8395 runs the event-message box (its row says start-up checks).
**Result.** 213 unflagged rows stay internal ("Re-checked with the corrected far calls." added); 273 flagged (116 tier A, 157 tier B). Of those, 21 changed status to notShown (19 routines and 2 stubs): the file side (Open Game's drive list and wrong-file alert, "Writing New Game File...", the PRS read / write error alerts, the file-in-use question, "file was busy" and "turn can't be saved" alerts, the revert question, the "game has been updated" alert, "do you want to save the changes", the start-up resource alerts), all kept differences of a browser game; 4 rows are real differences (below), and FUN_b000_562b (already notShown) turns out to be one too. The other 253 stay internal with a reason that now says what the routine really does (the alert box and its OK / Yes-No keys, the report text builders, the window makers and their procedures, the menu command handlers, window-library controls that reach only the cursor and pixel layer, the computer players' trace lines).
